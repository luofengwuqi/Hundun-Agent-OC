**体积依据（2026-11-13 实测）**：引擎运行必需 ≈ 627 MB（`node_modules` 362 + `dist` 265）；Node 24.22.3 单文件 122 MB（gzip 42.8 MB）。Node 仅占「引擎 + Node」总和的 **16%**——省这一成半而让首次启动依赖网络，不划算。

**为什么是「PATH 前置」而不是「复制到 `tools/cli-node`」**：

1. **复制会重复写 122 MB**，而且写在用户数据目录里——首启多等一次磁盘写入，还多一份要跟着升级的副本。两份副本迟早不同步。
2. **PATH 前置是文档里列明的候选**（`docs/install/node.md`：候选顺序为私有运行时 → 托管服务记录的 Node → **PATH** → nvm/fnm/Volta/Homebrew），每个候选都要过同一套 SQLite 能力检查，第一个通过的直接复用。我们捆的 Node 过得了。
3. 壳本来就用**绝对路径** spawn，不依赖 PATH；前置 PATH 是为了让引擎自己起的子进程、以及壳调用的 `models status --probe` 这类 CLI 也用同一个 Node，避免「主进程用 24、子命令用 22」的错配。

**⚠️ 一个不能想当然的细节（已查证，与直觉相反）**：上游私有运行时的目录布局**不是** `tools/cli-node/bin/node`。`node-runtime-update.mjs` L47–58 显示它把 `tools/cli-node` 当作**前缀**，真正的可执行文件在：

```text
<OPENCLAW_HOME>/tools/cli-node/tools/node/bin/node      # POSIX
<OPENCLAW_HOME>/tools/cli-node/tools/node/node.exe      # Windows
```

所以**不要**为了「让上游 recovery 找到」而手搓一个 `cli-node/bin/node`——它找不到。本决策因此不依赖 recovery：我们用绝对路径 spawn，PATH 只是兜住子进程。若日后确实需要往 recovery 目录放东西，**先按上面这个层级验证**，别按字面猜。

**这条决策承认的代价（不粉饰）**：

1. **构建矩阵 ×4**：win-x64 / mac-x64 / mac-arm64 / linux-x64，每个平台单独打一份 Node。
2. **Node 安全更新要跟发版**。这是真债：用户装完就不再自动获得 Node 的安全修复。缓解手段是发版节奏，不是技术方案——**要在发布流程里写明「Node 有安全公告时，本 app 必须跟版」**。
3. 安装包在 627 MB 引擎之上再加一成。

**这条决策解决了什么**：原设计把记忆放在应用数据目录（Linux `~/.config/…`）。卸载器会连它一起删——**那等于删掉一个人的所有日记**。而「卸载时打包成 zip 放桌面」在技术上挂不住：Linux 的 AppImage 根本没有安装/卸载概念，没有钩子可触发。

所以改的不是钩子，是落点：**记忆放在卸载器不会碰的地方，卸载后它本来就在原地**，不需要临终抢救。

**两条必须遵守的实现纪律**：

1. **用 `app.getPath("documents")`，不许手拼 `~/Documents`**。Windows 上「文档」可能被重定向到 OneDrive，Linux 上取决于 XDG 配置，手拼必错。
2. **测试不许写真实文档目录**。`dev-engine-smoke.mjs` 造一个假 documents 目录传进去，否则跑一次测试就往用户文档里塞一份假记忆。

**承认的代价与风险**：

1. **凭据跟着记忆走**。`openclaw.json` 里有 gateway token，模型 API key 也可能在同一处。好处是换机器时「把文件夹带走就能继续用」——这正是核心体验要的；坏处是**这个目录一旦被备份/同步/分享，凭据一并泄露**。（`configFile` 写入时已设 0600，但这挡不住用户主动打包分享。）
2. 文档目录常被 OneDrive / iCloud / 坚果云同步。同步盘对频繁改写的 SQLite 有冲突风险，最坏情况是状态文件损坏（记忆的 markdown 部分不受影响）。**打包时要决定是否给 `state/` 加排除规则**，见 O14。

### D026 关窗语义：托盘常驻，托盘退出才算真退

- 内容：点窗口关闭按钮 → **只隐藏窗口，应用与引擎继续运行**，驻留系统托盘；**托盘菜单里的「退出」才停引擎并退出**。
- 状态：已确认
- 确认人：用户
- 确认方式：直接陈述（「只不显示 但是还在系统托盘跑 但是系统托盘再关闭就是真的关了」）
- 确认日期：2026-11-13
- 来源：G17
- 适用版本：实施期
- 影响：`main.ts` 的 `window-all-closed` / `before-quit` 逻辑需改；需要托盘图标与菜单
- 替代：关窗即退出（原设计，落选）

**这条不只是平台习惯，是功能前提**：D014 定了「一天随机时间主动关心一次」。**关窗就退出的应用，永远等不到那次问候**——用户关掉窗口的那一刻，主动关心就死了。所以托盘常驻是 F-主动关心的必要实现条件，不是可选的体验优化。

**由此产生的两条约束**：

1. **必须有明确的「还活着」提示**。用户点了红叉以为关了，实际还在跑——托盘图标必须在，且退出路径要能一眼找到。否则这是欺骗。
2. **三平台一致：Windows / Linux 与 macOS 同样常驻托盘。** 2026-11-17 用户确认（原 O15）。若只在 mac 上常驻，D014 的主动关心就只在 mac 上生效——那等于同一个产品在不同系统上是两个东西。

**落地状态（2026-11-17）：已实现并四项实测通过。**

| 验收项 | 结果 |
| --- | --- |
| 点关闭 → 只隐藏，引擎不退 | ✅ 进程存活、引擎继续监听 18890 |
| 托盘「退出」→ 真退出 | ✅ 壳与引擎双双退出、端口释放、零孤儿 |
| 单实例锁（第二次启动叫回原窗口） | ✅ 第二实例立即退出、原实例存活、引擎精确 1 个 |
| 窗口被叫回后可见 | ✅ `visibility: visible` |

实测细节见 `SHELL-SKELETON.md` §4.4。**一条要记住的教训**：`forceQuit` 与 `before-quit` 的 `quitting` 标志必须成对存在，写反的三种方式（漏 `forceQuit` / 漏 `quitting` / 直接放行不 stop 引擎）会产生三种完全不同的症状——「点了没反应」「退出卡死」「引擎变孤儿」。所以这条留了开发期专用 IPC 做自动化验证，发行版里不注册。

**托盘不能装样子**：Linux 上 AppIndicator 缺失时 `new Tray()` 可能**建出对象但不显示图标**——此时 `tray` 变量非空，`close` 拦截照旧生效，用户点了红叉窗口消失且**再也叫不回来**（没有图标可点）。所以创建失败必须把 `tray` 置 `undefined`，并回退「关窗即退出」。**没托盘绝不能 hide**，这是 §4.4 之外单独要守的一条。

| # | 事实 | 依据 |
| --- | --- | --- |
| 1 | **该端点默认关闭**：`gateway.http.endpoints.chatCompletions.enabled`（schema 原话 default: false）。不开它连 `/v1/models` 都是 404——它们属于同一组开关 | `dist/schema-base-*.mjs`；实测 404 → 开启后 200 |

### O10 勘察结论（2026-11-13，对**实际运行**的 2026.11.3 发布包实查）

**先说状态**：本机现在跑的是 **npm 装到 `~/.local/lib/node_modules/openclaw` 的 2026.11.3（847611d）**，不是源码仓库里那份 2026.10.10 的 `dist/`。两者差一个版本，此前所有结论都基于旧的那份——所以这次全部在**新版本上重查**，不套用。

**三条硬事实**：

| # | 事实 | 依据 |
| --- | --- | --- |
| 1 | 工具面可以配置清零：`tools.profile: "minimal"` 只留 `session_status` + `gateway`(update) | `docs/gateway/config-tools/tool-policy.md` |
| 2 | 第三方插件从 `~/.openclaw/extensions` 与 `<workspace>/.openclaw/extensions` 加载，另有 `plugins.load.paths`；**不需要改包内任何文件** | `docs/gateway/config-extensions.md` |
| 3 | 危机干预内容在 2026.11.3 仍**零命中**（`suicide` / `self-harm` / `危机干预` / `心理援助` 在 `dist/` 与 `docs/` 均为 0 文件） | 实查 grep |

**为什么「改 `src/` 再 fork」不合理**（四个理由，按分量排）：

1. **升级即失效**。装的是 npm 包，`openclaw update` 会整包替换（CHANGELOG 里连「回滚到原包」都有实现）。任何改在 `dist/` 里的字节都会被下一次升级抹掉。要让它活下去，就得自己维护一条发布链——**本项目是单人造的陪伴 app，不是发行版**。
2. **改 `src/` 实际拿不到额外能力**。上面三条事实说明：想摘工具，配置就够；想插手对话，插件就够。改源码换来的边际能力，目前一处也没有。
3. **插件边界是设计好的**。`plugins.entries.<id>.hooks.allowPromptInjection` 这种开关存在，说明「谁能改提示词」是被核心显式管着的——这是给第三方留的口，不是要你 fork。
4. **许可上没问题，工程上有问题**。MIT 允许改；但改了的版本只有你一个人能合，上游每次修 bug 你都要手工搬一次。

**唯一必须写代码的地方：危机干预（O05）。** 上游没有内容安全分类器（事实 3），提示词层兜不住极端情况（模型会漏）。可行做法是插件挂在 `before_prompt_build`（2026.11.3 的 `dist/` 里该钩子出现在 36 个文件中，`agent_turn_prepare` 7 个、`heartbeat_prompt_contribution` 6 个，均**在新版本上确认存在**）。这是在插件边界内写代码，**不碰上游一行**。

**顺带查实的两条，供后续决策参考**：

- **记忆仍然只读**：内置记忆工具是 `memory_search` / `memory_get`，**没有写或删的工具**（`docs/concepts/active-memory/memory-tools.md`）。所以 `FEASIBILITY-A.md` 的 G3「记忆无遗忘工具」在新版本上依然成立。但「遗忘」不必动引擎——壳可以直接操作状态文件；代价是依赖未公开的存储结构，升级可能变。这条留到记忆方案定稿时再裁。
- **D014 的 pacing 仍存在**：`docs/automation/cron-jobs/schedules.md` 等 4 个文件在 2026.11.3 仍讲 pacing，D014 不因版本变化失效。

**一句话结论**：「动 OpenClaw 代码」如果指**改上游源码**——不合理，且没必要；如果指**在插件边界内写代码**——合理，而且是唯一能兜住 O05 的路。两者成本差一个数量级，别混在一个词里讨论。

### O08 勘察结论（2026-11-13，源码与文档实查）

**事实一：上游自己会找、也会装 Node。** `docs/install/node.md` 记载：当前 Node 不兼容时，启动会依次探测「私有 OpenClaw 运行时 → 托管 Gateway 服务记录的 Node → PATH → nvm/fnm/Volta/Homebrew」，每个候选都要过同一套 SQLite 能力检查，第一个通过的会被直接复用（"retries the original command without prompting"），并把该 Node 目录前置到子进程 PATH。私有运行时目录为 `~/.openclaw/tools/cli-node`，**或 `OPENCLAW_HOME` 指向的 home 下的同路径**。

**事实二：这套自动安装不会替壳干活。** 文档明写：`Startup recovery in non-interactive, CI, JSON, and --yes invocations never prompts or installs Node.js.` 壳是 spawn 子进程，永远非交互 → **「首次启动联网装」这条路，指望上游自动完成是不成立的**，必须壳自己实现下载与校验。

**事实三：`OPENCLAW_HOME` 能把状态整体搬进 app 目录。** `docs/help/environment.md`：设置后替换 `os.homedir()` 用于「默认状态目录、配置路径、agent 目录、**凭据**、installer 工作区」。优先级 `OPENCLAW_HOME > $HOME > USERPROFILE > ...`。另注：`OPENCLAW_HOME` 不取得 OS 账户原生 Gateway service 的所有权——本项目走前台 spawn，不受此限。

**由此得出的壳启动形态（待裁决后写入 `SHAPE-ELECTRON.md`）**：

```text
OPENCLAW_HOME=<app userData>/engine
<app>/runtime/node/bin/node <app>/engine/dist/index.js \
  gateway run --bind loopback --auth token --port <空闲端口> --allow-unconfigured
```

- 把预编译 Node 放在 `<OPENCLAW_HOME>/tools/cli-node`，上游 recovery 会**自己认出来**，壳不必另写探测逻辑，CLI 子命令（如 `models status --probe`）也不会再触发联网。
- `OPENCLAW_HOME` 指到 app 的 userData，则**配置、凭据、SQLite 记忆全在 app 目录内**，既不污染用户 `~/.openclaw`，也不会和用户自己装的 openclaw 串状态。这是「能安装的 app」该有的隔离度。
- `--auth token` + `--bind loopback` 是必须显式给的：`auth` 的合法取值里包含 `none`，桌面应用不能把「无鉴权的本地端口」当默认（`gateway run --help` 实查，2026-11-13）。

**候选对比（2026-11-13 实测体积，不再是「数十 MB」这种模糊说法）**：

先摆基准数（本机实测，`du` / `ls` / `gzip -c | wc -c`）：

| 对象 | 未压缩 | 压缩后（≈下载量） |
| --- | --- | --- |
| openclaw `node_modules` | 362 MB | — |
| openclaw `dist` | 265 MB | — |
| openclaw `docs`（运行不需要） | 23 MB | — |
| **引擎合计（运行必需）** | **≈ 627 MB** | — |
| Node 24.22.3 单文件 `node` | **122 MB** | **42.8 MB** |

| 候选 | 安装包增量 | 首次启动 | 主要利 | 主要弊 |
| --- | --- | --- | --- | --- |
| **A 随包捆**，落到 `<OPENCLAW_HOME>/tools/cli-node` | +122 MB（未压缩）；压缩后约 +43 MB | **离线即可用** | ①即开即用，不赌网络；②Node 版本确定，不受用户环境干扰；③放进上游认的位置，recovery 自动复用，壳不用写探测；④上游 `doctor`/`update` 的相关逻辑照常工作 | ①构建矩阵 ×平台数（win-x64 / mac-x64 / mac-arm64 / linux）；②Node 安全更新要跟发版，否则用户长期停在旧 Node；③安装包在 627 MB 引擎之上再加一成 |

**量化后的判断（比「我倾向 A」有分量）**：

Node 的 122 MB 只占「引擎 627 MB + Node 122 MB = 749 MB」的 **16%**。也就是说，选 B 省下的是一成半的体积，赌上的是「第一次打开能不能用」。

对一个「用户疲惫而迷茫时打开」的产品（D011），这个交换不划算——不是因为 43 MB 不心疼，而是因为**第一次打开就卡在下载上，用户不会再打开第二次**。

故仍推荐 A；B 只在一个前提下可取：产品明确接受「首次启动需要联网」，并且愿意维护下载链路。这个前提目前没人确认过，**属 O08 待裁范围，不得由实施方默认**。


### O11 候选解（2026-11-13，为 X03 提出，未选）

先摆清机制，否则三条候选看起来只是口味差异：

| 写路径 | 谁在写 | 靠什么 | `minimal` 下是否还活着 |
| --- | --- | --- | --- |
| ① compaction 前 memory flush | **模型**，调 `write` 写日常笔记 | 通用 fs 工具 | **死**（`write` 被摘） |
| ② Dreaming（默认开启） | **核心**，`tool-free completion` 改写 `MEMORY.md` | 后台 cron，不经模型的手 | **活**（不受工具策略约束） |

所以 `minimal` **不等于记忆断掉**，等于「记忆从即时变延迟」。这决定了三条候选的代价各不相同：

**A. `minimal` + 精确 `alsoAllow` + 自建窄写工具插件（推荐）**

```json5
{
  tools: {
    profile: "minimal",
    alsoAllow: ["memory_search", "memory_get", "remember_note"],  // remember_note 由自建插件提供
  },
}
```

- 插件只暴露一个「把一段文字追加到指定记忆文件」的工具，**没有通用读写、没有 exec**。
- 记忆即时性保住，工具面仍然接近零。
- 代价：多写一个插件（B 层，D019 已允许）。与 O05 的危机干预插件可以合并成同一个插件包，**一份工程量办两件事**。

**B. `minimal` + `alsoAllow: ["read", "write"]` + sandbox 限 workspace**

- 不动代码，配置就够，flush 原样工作。
- 代价是**不安全**：`write` 是通用写，agent 能改 `AGENTS.md` / `SOUL.md` / `IDENTITY.md`——用户一句「你换个性格」就可能把人格文件改掉。对陪伴产品这是隐患，不是洁癖。**不推荐。**

**C. 干脆不要 flush，只靠 Dreaming**

- 零代码、零工具面，`MEMORY.md` 仍会被后台改写。
- 代价：记忆变成「隔一段时间才想起来」。用户在当晚聊完关窗口，第二天打开可能「不记得」——这直接打在 D011 那句「很关键」上。**除非产品明确接受延迟记忆，否则不选。**

**一句判断**：A 比 B 安全、比 C 及时，代价只是一个插件；而那个插件本来就要写（O05）。所以真正的选择不是 A/B/C，而是**「愿不愿意让写记忆走一个窄工具」**。

题号归零不等于可以交付：实现层待裁、外部缺件、书面签认三类可能全部还挂着。
